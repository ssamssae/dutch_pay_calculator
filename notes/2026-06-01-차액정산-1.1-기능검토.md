# 더치페이 1.1 — "차액 정산 단발 입력" 기능 검토

- 과제: T-260515-11
- 작성: 2026-06-01 (🖥 데스크탑, loop-fleet dynamic)
- 성격: **검토/설계 문서. 코드 변경 없음.**
- 결론 한 줄: **넣자 (추천).** 단, "단발(one-shot) 정산" 으로 범위를 명확히 못박은 채로.

---

## 1. 검토 대상 기능

> "누가 얼마씩 냈는지 한 화면에서 입력하면, 누가 누구에게 보내야 하는지 바로 정산 결과를 알려주는 기능."

즉 각자 **실제로 낸 금액(불균등)** 을 입력 → 앱이 **누가 누구에게 얼마 송금** 하면 균형이 맞는지 계산. 이른바 settle-up / 채무 최소화(minimum cash-flow) 문제. Splitwise·토스 정산하기가 푸는 그 시나리오.

BACKLOG P2 의 "1.0.x → 1.1 기능 추가 — 본인 사용 피드백 채집 후 결정" 항목에 정확히 대응.

## 2. 현재 앱 구조 (실측)

`lib/main.dart` 단일 파일, 621줄, 화면 1개(`MainScreen`). 의존성은 Flutter SDK + `ads_service` 뿐 (상태관리 라이브러리 없음, 순수 `setState`).

현재 플로우 = **균등분할 한 종류**:
1. 커스텀 키패드로 `_digits` (총 금액) 입력 — 단일 문자열 상태.
2. +/- 버튼으로 `_personCount` (1~100) 조정.
3. `계산하기` → `_perPerson = _amount ~/ _personCount`, `_remainder = _amount % _personCount`.

핵심 상태는 `_digits`, `_personCount`, `_perPerson`, `_remainder` 4개뿐. **사람별 모델·이름·"누가 얼마 냈나" 개념이 전혀 없음.** 즉 1.1 은 기존 값 하나 바꾸는 tweak 이 아니라, 새 데이터 모델 + 새 화면이 필요한 **진짜 신규 기능면**.

## 3. 기존 플로우와의 맞물림

두 use case 는 **시점이 다른 별개 작업**이다:

| | 현재 (균등분할) | 신규 (차액정산) |
|---|---|---|
| 시점 | 결제 **전** ("이거 N명이 똑같이 나누자") | 결제 **후** ("각자 다르게 냈는데 이제 맞추자") |
| 입력 | 총액 1개 + 인원수 | 사람별 낸 금액 N개 |
| 출력 | 1인당 금액 + 나머지 | A→B 송금 목록 |

둘 다 정당한 "더치페이" 니즈라 한 앱에 공존이 자연스럽다. 가장 깔끔한 통합 = **상단 세그먼트 토글** (`균등분할` ⇄ `차액정산`). 현재 화면은 그대로 두고(기존 사용자 손실 0), 토글로 새 화면 진입.

## 4. 구현 난이도 — **중(中)**

- **정산 알고리즘: 쉬움 (~30줄).** 균등 fair-share = 총액 ÷ N. 각자 balance = 낸 금액 − fair_share. 양수=받을 사람(채권자), 음수=낼 사람(채무자). 채권자/채무자 최대값끼리 그리디 매칭 → 송금 건수 최소화. 캐주얼 앱엔 그리디면 충분 (이론적 최적 NP-hard지만 실사용 무차이). 나머지 1~2원 우수리는 마지막 채권자에게 몰아주기.
- **UI: 여기가 실제 작업량.** 사람 행(이름 optional + 금액)의 가변 리스트, 행 추가/삭제. 진짜 고민거리는 **커스텀 키패드 재사용** — 현재 키패드는 단일 `_digits` 에 박혀있음. 멀티 행 입력엔 "지금 편집 중인 행" 개념(active row index)이 필요. 키패드를 active 행에 연결하면 UX 일관성 ↑ 작업량 ↑.
- **상태:** `List<Person{name, paid}>` + activeIndex. 라이브러리 없이 `setState` 로 충분 (앱 규모상 provider 도입 불필요).
- **테스트:** 정산 로직은 순수 함수라 단위 테스트 쉬움. 기존 `test/widget_test.dart`(156줄) 패턴에 추가.

대략 잘 다듬어 1~2일. 알고리즘이 아니라 키패드-행 바인딩 + 결과 시트 폴리시가 시간을 먹음.

## 5. 가치

- **차액정산이 사실상 더 비싸고 끈적한 use case.** 균등분할은 OS 계산기로도 거의 되고 경쟁 앱도 흔함. "불균등하게 낸 뒤 누가 누구에게" 가 진짜 아픈 현실 시나리오(저녁은 A가, 카페는 B가, 택시는 C가 결제). 모임 끝나고 실제로 켜게 되는 기능 = 장난감 계산기를 실사용 앱으로 전환.
- 본인 사용 피드백 기반 결정(BACKLOG P2)이라면, 이게 1.1 1순위.
- **리스크: Splitwise 스케일로 scope creep.** "단발 입력" 프레이밍이 정확한 가드레일 — one-shot 유지, 계정·로그인·이벤트 히스토리 없음. 이게 경량 차별점(가입 0, 즉시). 이 선을 넘기 시작하면 별 앱이 됨.

## 6. UX 안 (2개)

### 안 A — 상단 세그먼트 토글 + 키패드 공유 (추천 타깃)
- 최상단 segmented control: `균등분할`(현행 그대로) / `차액정산`(신규).
- 차액정산: 스크롤 가능한 사람 행 리스트(이름 optional + 금액). 행 탭 → active → 하단 **공유 키패드**가 그 행 금액 편집. `+ 인원` 으로 행 추가. `정산하기` → 최소 송금 결과 시트.
- 장점: 시그니처 키패드 유지, 단일 일관 앱, 기존 사용자 손실 0. 단점: 키패드↔active 행 바인딩이 제일 까다로움.

### 안 B — 표준 키보드 경량판 (fallback)
- 현행 메인 화면 무수정. 별도 `정산` 진입에서 커스텀 키패드 대신 **시스템 숫자 키보드 + TextField** 행(이름+금액)으로 입력.
- 장점: 작업량·리스크 최소, 가장 빨리 출시. 단점: 입력 패러다임 2개(커스텀 키패드 vs 시스템 키보드)라 일관성 ↓.

**전략: A를 타깃, 첫 빌드에서 키패드 통합이 무거우면 B의 입력 단순함으로 후퇴.** 알고리즘·결과 화면은 A/B 공통이라 후퇴 비용 작음.

## 7. 범위 가드 (넣는다면)

- 균등 fair-share 가정(총액 ÷ N). "각자 부담액 다름"(가중치, 누구는 술 안 마심)은 **1.2 로 명시 제외** — 1.1 은 균등 분담 전제의 차액정산만.
- 계정·로그인·정산 히스토리·푸시 없음. **단발 one-shot 만.**
- iOS-only 배포 정책 유지(README §배포 정책). 신규 기능도 동일.

## 8. 결론·추천

**넣자.** 균등분할 화면이 못 푸는 "사후 불균등 정산" 이라는 최고가치 시나리오를 덮으면서, "단발" 제약이 Splitwise 스케일 creep 을 차단. 난이도는 중(대부분 UI), 알고리즘은 사소. 권장 형태 = **세그먼트 토글로 진입하는 단발 정산 모드 + 그리디 최소송금, 계정·히스토리 없음.** 첫 빌드 리스크는 키패드 재사용 한 곳에 몰려있으니, 거기서 막히면 시스템 키보드(안 B)로 즉시 후퇴.
